 STEP 1/11  BUILD THE DATABASE
================================================================================================
 We create an in-memory analytical database with the TPC-H schema (customers, orders, line
 items, parts, suppliers). The same eight tables are used by every query in the study, so any
 difference in speed between two queries comes from how they are written and planned, not from
 the data.

================================================================================================
 STEP 2/11  BUILD THE MATCHED THREE-ARM WORKLOAD
================================================================================================
 Each business question (an 'intent' taken from TPC-H) is written five ways: the official
 expert SQL, SQL produced by an ORM library (SQLAlchemy Core), and three different LLM-agent
 wordings. All five share the same parameter values, so the only thing that differs between
 them is the wording.
------------------------------------------------------------------------------------------------
 12 intents x 4 parameter draws x 5 formulations = 240 query instances.

 Example intent Q21, draw 0. Question: Suppliers in IRAQ who were the only late supplier on multi-supplier finished orders, top 100 by count.
   [expert ] select s_name, count(*) as numwait from supplier, lineitem l1, orders, nation where s_suppkey = l1.l_suppkey and o_orderkey = l1.l_orderkey and o_orde ...
   [orm    ] SELECT supplier.s_name, count(*) AS numwait FROM supplier JOIN lineitem AS l1 ON l1.l_suppkey = supplier.s_suppkey JOIN orders ON orders.o_orderkey =  ...

   [agent2 ] SELECT s.s_name, COUNT(*) AS numwait FROM supplier s JOIN nation n ON n.n_nationkey = s.s_nationkey JOIN lineitem l1 ON l1.l_suppkey = s.s_suppkey JOI ...
   [agent3 ] SELECT s.s_name, COUNT(*) AS numwait FROM supplier s JOIN nation n ON n.n_nationkey = s.s_nationkey JOIN lineitem l1 ON l1.l_suppkey = s.s_suppkey JOI ...

================================================================================================
 STEP 3/11  CHECK THAT EVERY WORDING RETURNS THE SAME ANSWER
================================================================================================
 A fast query is useless if it is wrong, so every ORM and agent query is compared with the
 expert query on the main database and on two smaller, randomly mutated databases. A wording is
 accepted only if it returns exactly the same rows everywhere. Agreement on mutated data guards
 against queries that are only right by luck.
------------------------------------------------------------------------------------------------

  agent   rejected        1
 expert  reference       48
    orm equivalent       48
 239 of 240 query instances are verified and go into the speed comparison. Rejected or
 unverified wordings are reported as a correctness result and excluded from timing.

================================================================================================
 STEP 4/11  QUERY FINGERPRINTING ENGINE
================================================================================================
 Every query is parsed into a syntax tree. The syntactic fingerprint ignores constants and
 formatting (what tools such as pg_stat_statements and AQO key on). The semantic fingerprint
 first applies safe rewrites (qualify columns, unnest subqueries, merge CTEs, normalise
 predicates) and keeps only the tables and predicates, so that different wordings of one
 question can share a key.
------------------------------------------------------------------------------------------------

 'orders joined to lineitem with the same filters'). Their true row counts are equal, so their
 estimates should be equal too (coherence law L1). Here we measure how often the estimator

 mark join from a subquery, CTE scan, ...).

================================================================================================
 STEP 8/11  INVACARD: FORMULATION-INVARIANT CARDINALITY CORRECTION
================================================================================================
 InvaCard corrects the optimizer's row estimates. It remembers true row counts under the
 meaning of each sub-expression (not its wording), learns a residual correction with gradient-
 boosted trees, only applies a learned correction when it is outside a conformal uncertainty
 band for that formulation path, and projects its outputs so that they obey the coherence laws.
 Protocol P1 trains on expert and ORM queries only and tests on the agent wordings it has never
 seen; protocol P2 holds out a whole question.
------------------------------------------------------------------------------------------------

================================================================================================
 STEP 9/11  STAGE ONE: PREDICTING REGRESSIONS BEFORE EXECUTION (M1 TO M5)
================================================================================================
 The guard must decide before a query runs, so it may only use the SQL text, the catalog and
 the EXPLAIN plan. As the review asked, we compare four detectors: M1 novelty only, M2
 complexity only, M3 plan features only, M4 all three combined, plus M5 = M4 with the coherence
 certificate. We test two situations: (A) the guard has seen the question before but with other
 parameter values (leave-one-draw-out), and (B) the question is completely new (leave-one-
 intent-out, the harder case). Area under the precision-recall curve (AUPRC) is the main score
 because regressions are rare.
------------------------------------------------------------------------------------------------
 Positives (measured regressions) among 239 verified queries: 16 (base rate 6.7%); a detector
 that guesses scores AUPRC = 0.067.

================================================================================================
 STEP 10/11  TIER B: CONTROLLED FAULT INJECTION AND EXACT CAUSE SHARES
================================================================================================
 A slow query is not automatically the optimizer's fault. For a sample of queries we switch
 four causes on and off in every combination: W = the agent's wording vs the fastest equivalent
 wording, P = the native plan vs the best alternative optimizer configuration, K = CPU
 contention from background queries, R = restricted resources (1 thread). Shapley values then
 split each slowdown exactly among the four causes. We also run the leakage test: stage-one
 inputs must not change when only the runtime conditions (K, R) change.

 runtimes we replay what each policy would have done for every query, using the out-of-sample
 risk scores of the M4 detector. We count regressions prevented and unnecessary interventions
 on healthy queries, and draw a decision curve: the net benefit of acting at each risk
 threshold compared with acting on all or none.
