Step 1. Build the database

We create an in-memory analytical database with the TPC-H schema (customers, orders, line items, parts, suppliers). The same eight tables are used by every query in the study, so any difference in speed between two queries comes from how they are written and planned, not from the data.

Step 2. Build the matched three-arm workload

Each business question (an 'intent' taken from TPC-H) is written five ways: the official expert SQL, SQL produced by an ORM library (SQLAlchemy Core), and three different LLM-agent wordings. All five share the same parameter values, so the only thing that differs between them is the wording.

12 intents x 4 parameter draws x 5 formulations = 240 query instances.

Example: five wordings of the same question (Q21)

Step 3. Check that every wording returns the same answer

A fast query is useless if it is wrong, so every ORM and agent query is compared with the expert query on the main database and on two smaller, randomly mutated databases. A wording is accepted only if it returns exactly the same rows everywhere. Agreement on mutated data guards against queries that are only right by luck.

Step 4. Query fingerprinting engine

Every query is parsed into a syntax tree. The syntactic fingerprint ignores constants and formatting (what tools such as pg_stat_statements and AQO key on). The semantic fingerprint first applies safe rewrites (qualify columns, unnest subqueries, merge CTEs, normalise predicates) and keeps only the tables and predicates, so that different wordings of one question can share a key.

Step 5. Measure real latency and build independent labels (Tier A)

Following the review feedback, we first measure real slowdowns. Each verified query is (a) explained without running it, which is all the guard may see, (b) run once with profiling to record the estimated and the true row count of every plan step, (c) timed with its own plan, and (d) timed under five alternative optimizer configurations (hint sets) that force different plans. Labels come only from these measurements, never from the guard's own rules.

Step 7. Formulation-path bias and the coherence certificate

Two wordings of the same question contain many identical logical sub-expressions (for example 'orders joined to lineitem with the same filters'). Their true row counts are equal, so their estimates should be equal too (coherence law L1). Here we measure how often the estimator breaks this, and how its error depends on the formulation path (plain join, semi/anti join, mark join from a subquery, CTE scan, ...).

Step 8. InvaCard: formulation-invariant cardinality correction

InvaCard corrects the optimizer's row estimates. It remembers true row counts under the meaning of each sub-expression (not its wording), learns a residual correction with gradient-boosted trees, only applies a learned correction when it is outside a conformal uncertainty band for that formulation path, and projects its outputs so that they obey the coherence laws. Protocol P1 trains on expert and ORM queries only and tests on the agent wordings it has never seen; protocol P2 holds out a whole question.

Step 9. Stage one: predicting regressions before execution (M1 to M5)

The guard must decide before a query runs, so it may only use the SQL text, the catalog and the EXPLAIN plan. As the review asked, we compare four detectors: M1 novelty only, M2 complexity only, M3 plan features only, M4 all three combined, plus M5 = M4 with the coherence certificate. We test two situations: (A) the guard has seen the question before but with other parameter values (leave-one-draw-out), and (B) the question is completely new (leave-one-intent-out, the harder case). Area under the precision-recall curve (AUPRC) is the main score because regressions are rare.

Positives (measured regressions) among 239 verified queries: 16 (base rate 6.7%); a detector that guesses scores AUPRC = 0.067.

Step 10. Tier B: controlled fault injection and exact cause shares

A slow query is not automatically the optimizer's fault. For a sample of queries we switch four causes on and off in every combination: W = the agent's wording vs the fastest equivalent wording, P = the native plan vs the best alternative optimizer configuration, K = CPU contention from background queries, R = restricted resources (1 thread). Shapley values then split each slowdown exactly among the four causes. We also run the leakage test: stage-one inputs must not change when only the runtime conditions (K, R) change.

Step 11. Mitigation policies and decision curves

A guard is only useful if acting on its warnings helps more than it hurts. Using the measured runtimes we replay what each policy would have done for every query, using the out-of-sample risk scores of the M4 detector. We count regressions prevented and unnecessary interventions on healthy queries, and draw a decision curve: the net benefit of acting at each risk threshold compared with acting on all or none.
